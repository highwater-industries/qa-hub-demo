# qa-hub demo

qa-hub is a desktop console for engineers who run pytest against lab systems and
inspect the Postgres databases behind them. This is its real UI running against
a simulated backend with sample data, so nothing needs installing.

**[Open the demo](https://highwater-industries.github.io/qa-hub-demo/)** in any modern browser. To run it offline, open
**[qa-hub-demo.html](https://github.com/highwater-industries/qa-hub-demo/blob/main/qa-hub-demo.html)**, press **Download raw file**, and open the file
in a browser.

A two-minute guided tour starts on your first visit; the longer written tour is below.
Nothing runs, connects or leaves your browser, and edits reset when you reload.
The desktop app itself is Tauri 2 + Rust with a Svelte 5 UI; its source is private.

## Tour

The navigation rail has five areas. The top bar includes the Profile menu, the
**bench switcher**, **Ctrl K** to jump anywhere, the current-run status, and
Capture.

1. **Run a test and watch it live.** In **Tests**, pick *Full demo suite
   (slow)* and select **Run**. The Output tab streams the pytest log and shows
   progress for each test. The run status in the top bar follows you throughout
   the app.
2. **Review the results.** When the run finishes, open the **Results** tab to
   see every test with PASS, FAIL, and SKIP filters. Select
   *test_order_backorder* to view the failure message. **History** shows earlier
   runs of the same Test.
3. **See how a Test is configured.** The **Configure** tab shows the bench,
   repository, virtual environment, environment packs, and pytest arguments.
   **Effective variables** shows which value wins at each layer. Select **Edit**
   to make changes.
4. **Browse tests in the repository.** Open the arrow beside **Run** and choose
   **Discover**. qa-hub finds tests and markers without running them. Select a
   test to run it directly or create a draft Test from it.
5. **Diagnose the failure.** Return to *test_order_backorder*, open its failure,
   and select **Diagnose run**. The Local Demo runner uses deterministic sample
   output without a Cursor key; with a key, your repository's diagnosis tool
   can use its own Cursor skills and playbooks.
6. **Review and improve the diagnosis.** A **Learning Proposal** suggests a
   playbook for this failure. Review the attempt, update the playbook, then use
   **Re-diagnose** and **Compare**. You can also ask a follow-up question and
   save a useful answer as another Learning Proposal.
7. **Spot flaky and regressed tests.** Go to **Results → Across runs**.
   *test_order_partial* is flagged flaky (it flips between pass and fail) and
   *test_order_backorder* regressed. Select it, then choose **Failure** on a run
   to see the message and the relevant lines from the run log.
8. **Open a bench.** **Benches** shows *LAB-1 (local)*: its variables, SSH
   hosts, database and recent runs. Use the bench switcher in the top bar to
   switch to *LAB-2 (staging)*; SSH, Transfer and the database list follow it.
9. **SSH and Transfer.** In **Benches → SSH**, select *LAB-1 controller* and
   enter any password. Try `systemctl status shelf-allocator --no-pager` or
   `tail -n 4 /var/log/allocator.log`. **Transfer** opens the same host as a
   two-pane file browser with an upload and download queue.
10. **Query the database.** In **Data → Queries**, open *Recent orders with
   payments* and select **Run query**. *All order lines (800k rows, streams to
   disk)* shows how large results load from disk as needed instead of filling
   memory.
11. **Explore the schema.** Open **Data → Graphs → Core schema** and select
   **Load graph**. Drag empty space to pan and drag a table to move it out of
   the way; it stays where you drop it until you double-click it. Click a table
   to select it, then **Query <table>** opens a query with its joins ready. Type
   a table in **Focus tables** and pick **Show around them** to narrow the graph.
12. **Collect evidence.** **Evidence → Caches** holds *Release 1.4 sign-off*:
    notes, log excerpts, and files gathered while testing. Export the collection
    as Markdown. Select text anywhere and press **Ctrl+Shift+E** to add it.
    **Recordings** stores SSH session transcripts.
13. **Switch Profiles.** Everything above lives in the *Local Demo* Profile. Open
    the **Profile** menu (top left) and pick *Release 1.5 team*. A Profile is a
    complete working context, so the benches (*RC-1*, *SOAK-1*), environment packs, Tests,
    saved queries, SSH hosts and run history all change at once; the bench
    switcher, SSH, Transfer and Data update with it. *Sandbox* is a personal
    scratch Profile. Switch back and *Local Demo* returns exactly as you left it.
14. **Keep a team Profile current.** *Release 1.5 team* represents a Profile
    generated by a test repository. In the Profile menu, choose **Import…**,
    keep the name *Release 1.5 team*, and select **Update**. The generated
    records refresh, a new query (*Backorders queued today*) appears under
    **Data → Queries**, and records created locally remain in the Profile.

Also try **Ctrl K** (type `orders`), and the light theme under **Settings**
(gear, top right).

## Profiles for a team

Use one Profile per team, release, customer site, or experiment. Each Profile
keeps its own benches, environment packs, Tests, connections, saved queries and
graphs, SSH hosts, open tabs, and history. Theme, cache budget, and shared
database connections remain global.

A test repository can generate a Profile JSON file from its bench manifest,
including benches, grouped hosts with roles and notes, database connections,
environment packs, saved queries, and ready-to-run Tests that point back to the
repository. Teammates import the file once. When the manifest or tests change,
run the generator again and choose
**Import… → Update**:

- Imported records are matched by ID and updated from the file.
- Records created by hand remain in the Profile.
- Records supplied by an earlier import are removed when the new file no longer
  contains them.
- Run history, recent items, open tabs, pins, and host connection status remain
  local.

**Replace** requires confirmation and makes the Profile match the file exactly.
Keep passwords out of generated files: qa-hub asks when it connects, and
**Settings → Credentials** keeps session passwords in memory only.
